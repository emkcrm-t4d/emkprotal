    Implement the conversion reversal domain service per ARCH-04, DEC-04 (D-04), and CONVERSION-SPEC.md Section 6:
    1. Create Exception `app/Domain/Members/Exceptions/InvalidConversionReversalException.php`:
       - RuntimeException returning HTTP 422
    2. Create `app/Domain/Members/Services/ConversionReversalService.php`:
       - Constants: `STATUTORY_CUTOFF_DAYS = 30`, `MIN_JUSTIFICATION_CHARS = 20`
       - Method `canReverse(Member $member): array`:
         - Returns `['allowed' => bool, 'reasons' => array]`
         - Evaluates:
           - Conversion timestamp diff in days <= 30
           - Member status is 'active'
           - No subsequent invoices exist (Invoice created_at > member created_at)
           - ID card status is not 'delivered'
       - Method `reverse(Member $member, string $justification, int $managerUserId): void`:
         - 1. Justification Guard: asserts `mb_strlen(trim($justification)) >= self::MIN_JUSTIFICATION_CHARS`. Throws `InvalidConversionReversalException` if fewer than 20 chars.
         - 2. Database Transaction: wraps all operations in `DB::transaction()`
         - 3. Lock Member: `Member::where('id', $member->id)->lockForUpdate()->firstOrFail()`
         - 4. Statutory Cutoff Guard: evaluates `Carbon::parse($lockedMember->created_at)->diffInDays(now()) <= 30`. Throws exception if > 30 days.
         - 5. Status Purity Guard: evaluates `$lockedMember->status === 'active'`. Throws exception if status is not active.
         - 6. Subsequent Activity Guard: checks `Invoice::where('member_id', $member->id)->where('created_at', '>', $member->created_at)->exists()`. If exists, throws exception.
         - 7. Card Handover Guard: checks `IdCard::where('member_id', $member->id)->where('status', 'delivered')->exists()`. If exists, throws exception.
         - 8. Cascading Rollback:
           - A. Update Member status to `archived_reversed`
           - B. Update portal User account: `is_active = false`, evict `remember_token`
           - C. Update post-conversion Invoice: `status = 'void_reversed'`
           - D. Update ID card: `status = 'voided_reversal'`
           - E. Restore Lead: status set back to `under_review`, `converted_member_id = null`. Crucially, verification history in `lead_verifications` and attachments are strictly preserved for re-inspection.
           - F. Append immutable audit event in `audit_logs`:
             - `event_type = 'conversion_reversed'`
             - `actor_id = $managerUserId`, `actor_guard = 'web'`
             - `auditable_type = Member::class`, `auditable_id = $member->id`
             - `old_values = ['status' => 'active']`, `new_values = ['status' => 'archived_reversed', 'lead_id' => $lead->id, 'restored_lead_status' => 'under_review']`
             - `reason = $trimmedJustification`
    3. Create feature test `tests/Feature/ConversionReversalServiceTest.php`:
       - Test successful reversal within 15 days with 25-character justification
       - Test cascading rollback: member is `archived_reversed`, invoice is `void_reversed`, card is `voided_reversal`, lead is restored to `under_review`
       - Test reversal blocked on Day 31 (statutory cutoff expired)
       - Test reversal blocked with justification under 20 characters
       - Test reversal blocked if physical card was marked `delivered`
       - Test reversal blocked if subsequent invoice exists
       - Test immutable audit log recorded with `conversion_reversed` event
  </action>
