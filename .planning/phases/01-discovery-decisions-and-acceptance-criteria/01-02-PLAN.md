         - Compliance Checklist items: `white_background` (pass/fail), `no_glasses` (pass/fail), `ears_visible` (pass/fail), `regular_attire` (pass/fail), `no_selfie` (pass/fail).

    Document:
    1. Lead Status Dictionary & State Transitions:
       - Statuses: `draft`, `submitted`, `under_review`, `missing_items`, `approved`, `converted`, `rejected`, `blocked`.
       - State Transition Matrix (From Status -> To Status -> Allowed Role -> Guard Condition -> Side Effects).
       - Reapplication & Blocking: Rejected applicants may reapply with clean form; reviewing staff see full historical rejection reasons. Workspace Managers hold authority to set email to `blocked` to stop abusive submissions.
    2. Atomic Lead-to-Member Conversion Protocol:
       - Invariant: Triggerable only by Workspace Manager when all 3 verification streams are `verified`.
       - Atomic steps:
         1. Create Member record copying verified applicant fields.
         2. Assign Member ID: format `{SPACE_CODE}-{YEAR}-{5_DIGIT_SEQ}` (e.g. `EMK-2026-00001`).
         3. Set Membership Start Date = Manager Approval Date per DEC-08 (D-08).
         4. Calculate Membership End Date dynamically from configured Term duration (e.g. +1 Year) — no hard-coded 2-year terms per DEC-08 (D-08).
         5. Re-associate uploaded private identity documents and photo with the new Member ID under safe generated storage filenames.
         6. Generate Post-Conversion Invoice with paid status reflecting verified bKash payment.
         7. Transition Lead status to `converted`.
         8. Queue welcome email with member portal activation link.
         9. Create initial ID Card record in `provided_for_printing` state.
         10. Write immutable conversion entry to append-only audit log per DEC-11 (D-11).
    3. Conversion Reversal Protocol (DEC-04 / D-04):
       - Authority: Workspace Manager only.
       - Prerequisites: Member must be within 30 days of conversion and have no subsequent transactions.
       - Mandatory Inputs: Reversal Reason string (minimum 20 characters) and Manager confirmation.
       - State rollback: Member record marked `archived_reversed`; associated invoices marked `void_reversed`; Lead status reverted to `under_review`; portal login disabled.
       - Audit event: Immutable event recorded with actor, timestamp, reason, and previous/new state snapshot.
    4. Member Status Dictionary:
       - Statuses: `active`, `inactive` (expired), `restricted` (Admin-restricted), `revoked` (Admin-revoked).
       - Admin Restrictions & Revocations: Member self-cancellation is strictly out of scope. Restriction or Revocation requires Global Admin or Superadmin authority, mandatory reason, and logged EMK management instruction.
    5. Configurable Membership Terms and Renewal Lifecycle:
       - Terms & Fees: Managed as database records (`membership_terms` table: name, duration_months, fee_bdt, active_flag).
       - Renewal Window: Opens exactly 30 days prior to membership expiry.
       - Early Renewal: Begins after current term expires. Late Renewal: Requires Manager confirmation and runs from approval date through selected term duration.
       - Renewal requests submitted through member portal do not require a new 31-field form; only bKash TxID and term selection.
    6. ID Card Issuance Lifecycle (3 Sequential States):
       - State 1: `provided_for_printing` (automatically created post-conversion or upon replacement request).
       - State 2: `card_printed_ready_for_pickup` (staff marks printed; triggers automated notification email to member).
       - State 3: `delivered` (staff logs delivery date and verifies physical recipient).
       - Card Replacement: Member or staff reports lost/damaged card; records replacement reason; generates replacement invoice/payment record if fee configured; restarts issuance lifecycle from State 1.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public Form Input → Server Validation | Untrusted user data submitted to server-side validation rules |
| Staff Reviewer → Verification States | Staff updating verification flags without proper payment/document evidence |
| Lead Conversion → Member State Creation | Transitioning unverified leads into active member records |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-04 | Tampering | Public Form Input Validation | high | mitigate | Re-validate all 31 fields on the server independently of client-side Alpine.js validations, enforcing strict regex and size limits per FIELD-DICTIONARY.md. |
| T-01-05 | Spoofing | bKash Transaction ID Replay | high | mitigate | Enforce database uniqueness constraint on bKash TxID across all Leads and Member Invoices, rejecting duplicate IDs at submission and verification per DEC-05 (D-05). |
| T-01-06 | Elevation of Privilege | Premature Lead-to-Member Conversion | critical | mitigate | Implement domain service gating invariant (`ConversionAllowed`) asserting all three verification states equal 'verified' inside an atomic database transaction per DEC-03 (D-03). |
| T-01-SC | Tampering | Package Manager Dependencies | high | mitigate | No package installs in Phase 1 discovery; software dependencies deferred to Phase 3 foundation with strict package legitimacy gates. |
</threat_model>
